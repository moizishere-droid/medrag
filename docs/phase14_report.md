# Phase 14: LLM Answer Generation — Report

## Phase Objective

Turn the reranked chunks produced by Phases 10-11 into an actual answer — a grounded, cited, natural-language response generated by an LLM using only the retrieved context, with structured facts from Phase 13's knowledge graph as an additional high-confidence signal for drug-related queries, and automatic response-language matching in line with the project's multilingual goal.

## What Was Built

- **`format_context()`** — formats reranked search results into a numbered context block for the prompt.
- **A layered system prompt**, built and validated incrementally: (1) grounded-only generation, (2) lightweight citation tagging, (3) multilingual auto-detection, (4) knowledge graph fact integration.
- **`get_all_known_drug_names()` / `find_mentioned_drug()`** — detects whether a query mentions a known OpenFDA drug, using the graph's own canonical name list rather than re-running NER.
- **`get_graph_facts_for_drug_curated()`** — pulls and cleans structured `TREATS`/`CAUSES`/`CONTRAINDICATED_IN` facts for a mentioned drug.
- **`generate_answer()`** — the full pipeline: hybrid retrieval + reranking → optional graph enrichment → grounded, cited, language-matching generation.
- **`backend/src/medrag/generation/`** — new package (`generation.py`, `__init__.py`).

## Key Design Decisions

1. **Model changed from the original plan (GPT-4-turbo) to `gpt-4.1-nano`.** Confirmed via research that GPT-4-turbo was fully retired from the OpenAI API (deprecated February 13, 2026; final legacy variants removed March 26, 2026) — well after this project's original Phase 0 scoping. The account's actual available models were checked directly rather than assumed; the newer GPT-5.6/GPT-6 family is not available on this account's usage tier. `gpt-4.1-nano` ($0.10/$0.40 per million tokens) was chosen deliberately for cost, appropriate for a student portfolio project rather than a funded production deployment. `gpt-5.2` (confirmed available) is documented as a tested fallback if generation quality proves inadequate on a given query — the model is a swappable parameter, not hardcoded.
2. **Grounding is enforced by explicit instruction, validated on both a strong and a weak query, not assumed to work from prompt wording alone.** The system prompt instructs the model to answer only from provided context and state plainly when context is insufficient. This was tested directly: a well-covered query produced a correct, detailed answer; the exact Phase 10/11 diagnostic query with known weak corpus coverage ("how does the body regulate blood sugar") correctly produced an honest "the context does not provide specific details" rather than a plausible answer drawn from the model's own training knowledge.
3. **Citations are lightweight and provisional by design.** The model tags claims with bracketed numbers referencing context blocks (e.g. `[1][3]`) — sufficient for this phase's purpose (proving the model can consistently produce a taggable reference) without building the real citation formatting/rendering system, which is Phase 15's dedicated responsibility.
4. **Multilingual handling is one prompt instruction, not a separate detection pipeline.** Rather than adding a language-detection library and passing a detected language code as a parameter, the LLM is instructed to detect the query's language itself and respond in kind. Validated on a genuinely difficult case: a Roman-script (Latin-alphabet) Urdu query, not written in Urdu's native script — the model correctly detected the language and responded in matching Roman Urdu.
5. **Knowledge graph facts are surfaced via substring matching against the graph's own drug list, not NER.** Since Phase 13's graph already contains the exact canonical name of every drug it knows about, checking whether a query mentions one of those 466 names directly is simpler and more reliable than re-running entity extraction on the query text.
6. **A real data-quality issue in the graph facts was found and fixed before use, not passed through silently.** Inspecting raw facts for a real drug surfaced a direct contradiction: the same disease appeared under both `TREATS` and `CAUSES` for the same drug (traced to Phase 13's already-documented residual NER noise). Fixed by dropping a `CAUSES` entry whenever its disease also appears under `TREATS` for the same drug, treating `TREATS` (from the more authoritative `indications_and_usage` section) as the higher-confidence source when the two conflict.
7. **`CAUSES` facts are capped, `TREATS`/`CONTRAINDICATED_IN` are not.** A drug can have dozens of listed adverse effects; including all of them would bloat the prompt and bury the clinically more important treats/contraindication facts. This is documented explicitly as a practical volume control, not a principled noise filter — some remaining noise entities may still appear within the capped set, an honest limitation rather than a claimed complete fix.
8. **The knowledge graph integration is optional at the function level (`neo4j_driver=None`).** Generation should not hard-depend on Neo4j being available — a caller can skip graph enrichment entirely (e.g. Neo4j is down, or the query type doesn't warrant it) without the core retrieval-and-generation path failing.

## Results

- **Grounded generation confirmed correct on both a strong and a weak retrieval case**, using the same two test queries validated across Phases 10-11, giving a direct before/after comparison across the whole pipeline (retrieval → reranking → generation) on the identical queries.
- **Citations verified plausible**: tagged claims matched the context blocks that actually supported them (e.g. a direct adverse-effects table cited as `[1]`, a related but distinct detail cited as `[3]`).
- **Multilingual capability confirmed on a genuinely hard case** (Roman-script Urdu), not just a straightforward native-script example.
- **Knowledge graph integration validated end-to-end**: a full-pipeline test query about metformin correctly incorporated both retrieved-chunk content and curated graph facts, with all four real contraindications (renal impairment, hypersensitivity, metabolic acidosis, diabetic ketoacidosis) appearing accurately in the final answer.
- **Production `generate_answer()` verified to exactly reproduce the notebook's results** on a full-stack integration test hitting Qdrant, Neo4j, and OpenAI together in one call — same facts, same citation pattern.

## Challenges & Solutions

- **The originally-planned model (GPT-4-turbo) no longer exists.** Resolved by researching current OpenAI model availability and pricing, checking the actual project account's accessible models directly (rather than assuming access to newer flagship families), and choosing a current, confirmed-available, cost-appropriate replacement with a documented fallback plan.
- **An initial 403 `model_not_found` error** on a first-choice model (`gpt-5.6-luna`) was resolved by listing the account's actual available models via the API rather than guessing at further model names.
- **A real contradiction in the knowledge graph's raw output** (a disease under both `TREATS` and `CAUSES` for one drug) was caught by inspecting actual data before wiring it into generation, not assumed clean because Phase 13's phase report had already documented a noise filter. This is treated as expected, healthy behavior of the project's methodology — data quality issues surfacing at a new usage point (here: reading many facts as raw text rather than checking aggregate counts) get investigated and fixed at the point they're found, rather than deferred.
